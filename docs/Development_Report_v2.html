홈런 숫자야구(Strike Four) 개발 보고서 (v2)

1. 개요

홈런 숫자야구(Strike Four)는 초등학교 교실에서 로그인 없이 바로 즐길 수 있는 숫자야구(불스앤카우) 웹 게임이다. 학생은 이름/닉네임만 입력하면 되고, 혼자 AI와 연습하거나 교사가 띄운 QR코드로 반 친구와 실시간 1:1 대전을 할 수 있다. v2에서는 반 전체가 참가하는 토너먼트/리그전이 추가되어, 한 차시 안에 우승자와 순위를 가리는 교실 이벤트로 확장되었다. 대상 사용자는 초등학교 교사와 학생이며, 전자칠판·디벗(태블릿)·스마트폰 등 다양한 화면에서 쓰이는 것을 전제로 한다.

2. 목표 및 배경

  • 핵심 가치: 회원가입/로그인 장벽 없이, 교사가 QR 하나만 띄우면 반 전체가 즉시 대전에 참여할 수 있게 하는 것.
  • v2의 목표: v1의 "자유 랜덤 매칭"만으로는 교사가 진행을 통제하기 어렵고 승부의 결론이 나지 않는다는 점을 보완해, 교사가 라운드를 진행하며 우승·순위를 정하는 대회 방식을 제공한다.
  • 진행 방식: v1과 같이 사용자가 실제 브라우저에서 확인하고 피드백을 주는 방식이 기본이었다. v2의 대회 기능은 사용자가 "제안 기본값에 동의한다"고 승인한 뒤 /autopilot으로 한 번에 구현했고, 이후 실사용 피드백(버그·디자인)을 짧은 주기로 반영했다.

3. 주요 기능

v1에서 이어진 기능

  • 혼자 연습하기(vs AI, 3단계 난이도, 시도 횟수 10~20회), 친구 초대, 학급 방 만들기(자유 랜덤 매칭), 실시간 1:1 대전(턴 동기화·판정·시간 초과 스킵), 결과 화면(트로피·컨페티·상대 정답 공개), 학급 랭킹, 파스텔/모던 테마.

v2에서 추가·변경된 기능

  • 토너먼트/리그전(메인 5번째 카드): 교사가 형식·턴 시간·시도 횟수를 정해 대회 방을 만들고, 학생은 기존 '방 참가하기'로 들어온다. 교사가 라운드를 시작하면 서버가 대진표대로 방을 만들어 학생이 자동 입장한다.
    • 토너먼트: 무작위 대진, 인원이 안 맞으면 1라운드 부전승. 무승부는 연장전(최대 2번) 후 동전 던지기. 결과는 우승/준우승/공동 3위.
    • 리그: 원 돌리기(circle method) 대진으로 라운드마다 전원이 동시에 1경기, 같은 상대와 중복 대결 없음. 승 3·무 1·패 0, 쉬는 라운드 1점, 순위는 승점 → 승수 → 이긴 경기 평균 시도 횟수.
    • 교사 운영 도구: 참가 마감·대회 시작, 다음 라운드, 경기별 몰수패/동전 던지기/무승부 처리, 참가자 제외, 대회 종료, 대회 취소, 새 대회 만들기.
  • 메인 화면 전적: 랭킹과 같은 기준(같은 학급, 같은 집계)으로 계산한 내 승-패를 프로필 카드에 표시.
  • 브라우저 '뒤로 가기' 지원: 하위 화면에서 뒤로 가기를 누르면 메인으로 이동(정리 동작 포함).
  • 턴 시간 50초 옵션 추가(20/30/40/50초).
  • 화면 디자인 개편: 토너먼트/리그전 허브·진행·결과 화면과 학급 방 만들기 화면을 같은 디자인 체계(머리글+카드+큰 글씨)로 통일. 메인 카드 글씨와 아이콘 확대, 카드 5장 반응형 배치.
  • 게임 화면 개선: 공격 기록 한 줄 높이를 약 45px에서 약 30px로 줄여 스크롤 없이 5줄이 보이도록 조정(숫자 카드/버튼은 디벗 사용을 고려해 유지).

v2 아키텍처 핵심 — "대회 = 특수한 학급 방"

  • 별도 시스템을 만들지 않고 sessions.mode(free/league/tournament)로 기존 학급 방을 확장했다. 학생은 기존 QR/코드 참가 흐름을 그대로 쓰고, 방의 mode에 따라 대회 대기 화면으로 분기한다.
  • 대회 방은 자동 매칭을 하지 않는다(match_waiting_players가 즉시 반환). 교사가 라운드를 시작하면 서버가 rooms/room_secrets를 만들고 session_players.room_id를 채우며, 학생 화면은 기존과 같이 이 변경을 구독해 자동 입장한다.
  • 테이블: tournaments, tournament_players, tournament_matches(익명 SELECT만 허용, 쓰기는 RPC 전용), tournament_admin(RLS만 켜고 정책이 없어 익명 조회 불가, 교사 브라우저에만 관리 토큰 발급).
  • 두 형식은 같은 "라운드" 엔진을 쓰고, 대진 생성·무승부 처리·순위 계산만 다르다. finish_room()에 훅을 추가해 대회 경기가 끝나면 tournament_on_room_finished()가 승패 반영·진출·연장전을 처리한다.

5. 개발 과정 (타임라인)

v1(Phase 0~7, 배포, 개발 보고서·전역 스킬 app-intro/development-report 작성) 이후 진행한 작업이다.

  1. Phase 6 이후 UI 배치 작업: 시도 번호 표시, 결과 화면 트로피·컨페티·상대 정답 공개, 교사용 방 설정, 용어 통일, S/B 배지 등(v1 보고서에 포함).
  2. 메인 화면 다듬기: 카드 글씨 확대 → 카드 안 아이콘 50% 확대(카드 크기 유지).
  3. 브라우저 뒤로 가기 구현: 하위 화면 진입 시 히스토리 항목 1개를 쌓고, popstate에서 기존 정리 동작(goHome)을 호출.
  4. 메인 전적 표시 버그 수정: 원래 0승 0패가 HTML에 고정된 글자였음을 발견. 처음엔 브라우저 저장 방식으로 구현했다가, "연습 결과는 빼고 랭킹과 동일하게"라는 요청에 따라 서버의 match_results에서 랭킹과 같은 방식으로 계산하도록 변경. 이후에도 갱신되지 않던 원인이 identity-ready 이벤트 타이밍임을 찾아 수정.
  5. 턴 시간 50초 옵션: DB 제약(turn_seconds 20/30/40)도 함께 확장.
  6. 토너먼트/리그전 계획 수립(/plan): 현재 DB 함수·정책을 조사해 설계 근거를 확보하고, 형식별 운영 방식·위험·인수 조건을 담은 계획서(.omc/plans/tournament-league-plan.md)를 작성. 사용자가 제안 기본값 5가지에 동의.
  7. 토너먼트/리그전 구현(/autopilot): T0(DB) → 클라이언트 → 통합 순으로 구현. DB 시뮬레이션(리그 3·4·5·8·9명, 토너먼트 4·5·6·8·13명)으로 대진 로직을 검증하고, jsdom 기반 화면 시뮬레이션 테스트를 작성. 보안 리뷰어·코드 리뷰어 에이전트의 지적 사항(부전승 조작 가능성, 잠금 순서, 정원 제한, 새로고침 복귀, 토큰 삭제 위험 등)을 반영.
  8. 실사용 피드백 반영: 턴 시간이 지나도 넘어가지 않는 문제, 3명 토너먼트 시작 불가, 대회 취소 기능, 디자인 개편, 버튼 크기 문제 등을 차례로 수정.
  9. 디자인 개선 요청: 학급 방 만들기 화면 통일, 게임 화면 공격 기록 줄 높이 조정.
  10. 개발 환경 개선: Playwright MCP가 다시 연결되어 로컬 서버(임시 포트)로 실제 화면 캡처를 확인하며 디자인을 다듬을 수 있게 되었다(v1의 "UI 테스트 수동" 한계가 일부 해소).

6. 주요 의사결정과 이유

  • 대회를 별도 시스템이 아닌 "학급 방의 모드"로 구현: 기존 QR 참가 흐름·자동 입장·실시간 구독을 그대로 재사용해 위험과 코드를 줄이고, 학생에게는 참가 방법이 하나로 유지된다.
  • 라운드 단위 단일 엔진 + 교사가 라운드 진행: 초등 교실에서는 교사가 학생 준비 상태를 보고 진행 속도를 통제하는 편이 안전해 자동 라운드 진행은 2차로 미뤘다.
  • 대진 생성을 서버(plpgsql)에서 수행: 학생 브라우저가 조작할 수 없고, SQL로 검증하기 쉽다.
  • 토너먼트 무승부는 연장전 최대 2번 후 동전 던지기: 항상 승자가 존재해야 진출이 결정되고, 교실 시간 안에 끝나도록 상한을 둔다.
  • 리그 부전 = 승점 1: 승 3점으로 주면 한 번 쉰 학생이 유리해지므로 무승부 상당으로 정했다.
  • 관리 토큰 방식: teacher_id가 공개되어 있어(학생이 조회 가능) 그것만으로는 관리 권한을 증명할 수 없으므로, 서버가 발급한 비공개 토큰으로 라운드 시작·취소·강제 처리 등을 통제.
  • 대회 경기 결과를 랭킹/전적에 반영(부전·동전 던지기 제외): 실제 1:1 경기이므로 학생 기대에 맞고, 메인 전적과 랭킹이 같은 데이터 원천을 유지.
  • 토너먼트 최소 인원 4명 → 3명: 실사용에서 3명으로 시작하려다 막힌 피드백을 반영(3명이면 1명이 부전승으로 결승 진출).
  • 공격 기록 줄 높이만 줄이고 버튼은 유지: 디벗을 쓰는 아이들을 위해 숫자 카드와 버튼은 큰 크기를 유지하기로 사용자가 결정.

7. 문제 해결 기록

  • 턴 시간이 지나도 턴이 넘어가지 않음(v1부터 잠재): 시간 초과를 서버에 알리는 코드가 .catch(...)를 호출했는데 Supabase 호출 객체(PostgrestBuilder)에는 catch가 없어 요청이 아예 전송되지 않았다. 서버 함수는 정상이었고 DB에는 마감이 한참 지났는데 스킵 기록이 없는 방이 남아 있어 단서가 되었다. .then으로 교체하고, 내 제한 시간이 끝나면 입력을 잠그며 3초 뒤 스스로 스킵을 요청, 서버(submit_guess)도 마감 후 입력을 거부하도록 보강했다.
  • 메인 전적이 갱신되지 않음: 전적 계산 함수 자체가 없었고(HTML 고정 글자), 이후에도 페이지 로드 시 identity-ready 이벤트가 리스너 등록 전에 동기 발생해 유실되었다. 이벤트 발생을 setTimeout 0으로 늦춰 해결했다(같은 원인으로 QR 링크 자동 참가·방 복귀도 새로고침 시 동작하지 않았을 가능성이 있었다).
  • plpgsql의 IF 조건 안 CASE 문법 오류: if n < case ... end then은 첫 THEN에서 조건이 끝난다고 해석되어 실패했다. 변수에 먼저 계산해 넣는 방식으로 수정.
  • "시작 버튼이 눌러도 진행 안 됨": 토너먼트 최소 인원을 4명으로 정해 놓았고 버튼 비활성 이유를 알려주지 않았다. 최소 인원을 3명으로 낮추고 버튼에 "N명 더 필요"를 표시.
  • 안내 상자 버튼이 세로로 거대해짐: 미디어쿼리보다 나중에 선언된 기본 규칙이 flex-direction을 덮어써 flex: 1 1 200px가 세로 방향 높이가 되었다. 안내 상자 버튼만 별도 규칙(flex: 0 0 auto)으로 분리.
  • 새 화면에서 제목이 가운데로 밀림: #screen-create-session에 걸려 있던 옛 가운데 정렬 규칙(ID 선택자, 우선순위가 높음)이 새 디자인을 덮어썼다. 해당 규칙에서 화면을 제외.
  • JS 리뷰에서 발견된 새로고침/복귀 문제: ?code=가 URL에 남아 새로고침마다 재참가하려는 문제, 네트워크 오류 시 관리 토큰이 삭제되는 문제, 연습 후 다음 라운드 자동 입장 구독이 끊기는 문제, 같은 방 중복 입장 문제를 수정.
  • 테스트 도구 한계 우회: bash 도구가 복잡한 heredoc을 파싱하지 못하는 경우가 반복되어 Write 도구로 스크립트를 만들고 실행하는 방식으로 우회했다.

8. 보안/성능 고려사항

  • 관리 RPC 인증: start_tournament, start_next_round, resolve_match, remove_tournament_player, finish_tournament, cancel_tournament는 모두 tournament_assert_admin(토큰 검증)을 먼저 호출한다. tournament_admin 테이블은 RLS만 켜고 정책이 없어 익명으로 읽을 수 없다.
  • 내부 함수 실행 권한 회수: finish_room(이전에는 익명이 직접 호출해 임의로 승자를 정할 수 있었다), tournament_* 내부 함수, 참가 가드 트리거 함수의 EXECUTE 권한을 anon/public에서 회수. 또 tournament_* 테이블의 TRUNCATE/TRIGGER/REFERENCES 권한도 회수.
  • 부전승 조작 방지: 이전 forfeit_room은 익명이 자기 ID로 호출하면 언제든 상대를 몰수패시킬 수 있었다. 이제 내 차례가 아니고 상대의 제한 시간(+10초)이 지났을 때만 인정하며, 대회 경기는 서버의 연속 3회 시간 초과 규칙(skip_turn)에만 맡긴다.
  • 잠금 순서 통일과 finish_room 멱등화: 방 행을 잠그고 이미 끝난 방이면 무시해, 교사 조작과 경기 종료가 동시에 일어나도 교착이나 중복 기록이 없도록 했다.
  • 참가 트리거: 대회 시작 후 신규 참가 차단, 정원 60명 상한, 참가 시 상태를 대기(waiting)로 강제.
  • XSS: 모든 화면은 textContent/DOM 생성으로 렌더링하며(닉네임 태그가 이스케이프됨을 테스트로 확인), 대회 방의 설정은 생성 후 변경할 수 없다(sessions_update_settings는 mode='free'만 허용).
  • 보안/성능 점검: 서브에이전트(보안 리뷰어)가 DB 계층을 검토해 HIGH 1건(부전승 조작)과 MEDIUM 1건(잠금 순서)을 지적했고 모두 수정했다.

9. 테스트 및 검증

  • DB 시뮬레이션(롤백 트랜잭션): 가짜 플레이어로 리그 3·4·5·8·9명, 토너먼트 3·4·5·6·8·13명을 끝까지 진행(전부 승리/전부 무승부 모드)해 중복 대결 0건, 부전 수, 라운드 수, 우승자 결정, match_results 기록 수를 확인. 마감 후 참가 거부, 연속 스킵 몰수패, 마감 후 입력 거부, 취소 시 진행 중 방 정리 등도 확인.
  • 접근 차단 검증: 익명 키로 finish_room 호출(권한 거부), 잘못된 토큰의 관리 RPC(거부), tournament_admin 조회(빈 결과), 대회 테이블 직접 INSERT(RLS 거부) 확인.
  • 화면 시뮬레이션(jsdom, 37개 항목): 교사/학생 화면, 순위표, 대진표, 우승 표시, 탈락 처리, 취소 흐름, 허브 정리, 턴 타이머의 스킵 요청 전송, 닉네임 이스케이프, 메뉴 카드 5장.
  • 실제 화면 캡처(Playwright + 임시 로컬 서버): 허브, 진행, 결과, 학급 방 만들기, 게임 화면의 모바일/데스크톱 레이아웃을 직접 확인(줄 간격 30.7px 측정 포함).
  • 미확인: 여러 실제 기기로 대회를 끝까지 진행하는 최종 확인은 사용자 테스트에 의존한다(연장전, 다음 라운드 자동 입장, 새로고침 복귀).

11. 알려진 한계

  • 교사가 브라우저 데이터를 지우면 그 대회의 관리 토큰을 잃어 대회를 계속 관리할 수 없다(새 대회를 만들어야 함).
  • 교사 브라우저를 새로고침하면 대시보드가 자동으로 열리지 않아 허브의 "대회 화면으로 가기"로 이어가야 한다.
  • 토너먼트 연장전은 학생/교사 화면이 열려 있어야 자동 시작된다(둘 다 닫히면 멈추며, 교사의 경기별 처리 버튼이 대안).
  • 접속을 끊은 상대 때문에 경기가 끝나려면 그 선수가 연속 3번 시간 초과해야 한다(턴 30초 기준 약 90초).
  • 로그인이 없어 같은 학생이 다른 기기로 접속하면 별도 사용자로 집계된다. 친구 초대 세션은 랭킹/전적에 집계되지 않는다.
  • 공격 기록이 6줄 이상 쌓이면 스크롤이 생긴다(카드 높이는 유지).
  • 오래된 세션 행 정리, 홀수 대기 인원 UX, 자동 UI 회귀 테스트는 여전히 미비하다(단, 화면 시뮬레이션 테스트 스크립트는 작업 폴더 밖에서만 존재하고 저장소에 포함되지 않았다).

12. 향후 개선 아이디어 / 업데이트 계획

다음에 하면 좋을 것

  • 토너먼트 연장전/다음 라운드를 서버가 시간 기준으로 자동 시작(DB 스케줄러 pg_cron)해 화면 의존을 없애기
  • 교사 대시보드 자동 복구(새로고침 시 마지막 대회를 자동으로 열기) 및 관리 토큰 백업/복구 수단

  • 홀수 인원/대기 인원 처리 UX, 리더보드 집계 기간 옵션, 닉네임 중복·부적절어 필터링

  • 대회 결과를 학급 랭킹과 분리해 보기(대회 전용 순위)
