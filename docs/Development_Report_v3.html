홈런 숫자야구(Strike Four) 개발 보고서 (v3)

1. 개요

홈런 숫자야구(Strike Four)는 초등학교 교실에서 로그인 없이 바로 즐길 수 있는 숫자야구(불스앤카우) 웹 게임이다. 학생은 이름/닉네임만 입력하면 되고, 혼자 AI와 연습하거나 교사가 띄운 QR코드로 반 친구와 실시간 1:1 대전, 반 전체 토너먼트/리그전을 할 수 있다. v3에서는 실제 초등학생 테스트에서 난이도가 높다는 피드백을 받아 3자리 숫자 모드를 추가하고 기본 모드로 삼았다. 대상 사용자는 초등학교 교사와 학생이며, 전자칠판·디벗(태블릿)·스마트폰 등 다양한 화면에서 쓰이는 것을 전제로 한다.

2. 목표 및 배경

  • 핵심 가치: 회원가입/로그인 장벽 없이, 교사가 QR 하나만 띄우면 반 전체가 즉시 대전에 참여할 수 있게 하는 것.
  • v3의 목표: 4자리를 위치까지 맞히는 규칙이 초등학생에게 어렵다는 현장 피드백에 따라, 규칙은 그대로 두고 자릿수만 줄인 쉬운 모드를 제공한다(가능한 조합 수 5,040 → 720).
  • 진행 방식: 사용자가 구현 전에 /plan으로 "전역 설정 vs 기능별 설정"을 비교해 한 가지를 추천받고, 승인 후 구현했다. 추천 과정에서 코드와 서버 함수를 직접 조사해 처음 제안 일부를 정정했다(아래 6장).

3. 주요 기능

이어진 기능

  • 혼자 연습하기(vs AI, 3단계 난이도, 시도 횟수 10~20회), 친구 초대, 학급 방 만들기(자유 랜덤 매칭), 실시간 1:1 대전(턴 동기화·판정·시간 초과 스킵), 결과 화면, 학급 랭킹, 파스텔/모던 테마.
  • 토너먼트/리그전(교사 운영 도구, 연장전·동전 던지기, 대진표·순위표), 메인 화면 전적, 브라우저 뒤로 가기, 턴 시간 20/30/40/50초.

v3에서 추가·변경된 기능

  • 3자리 숫자 모드: 규칙은 4자리와 같고 자릿수만 하나 줄었다.
    • 혼자 연습하기: 난이도 아래에 "3자리 / 4자리" 토글. 선택은 브라우저에 기억된다.
    • 학급 방 만들기: 게임 설정에 "숫자 자릿수". 방에 저장되어 학생은 바꿀 수 없다.
    • 토너먼트/리그전: 대회 설정에 "숫자 자릿수". 시작 후 변경 불가.
    • 표시: 3자리 방·대기실·대회 제목에 "3자리" 배지.
  • 기본값 3자리: 혼자 연습, 학급 방 만들기, 토너먼트/리그전 모두 기본 선택이 3자리(4자리로 바꿀 수 있음). 친구 초대는 4자리 유지.
  • 메인 화면에는 게임 모드 선택을 두지 않음: 학생이 바꿀 수 없게 하기 위함.
  • 칠판용 보기(전자칠판 화면): 교사의 토너먼트/리그전 화면에 "🖥️ 칠판용 보기" 버튼을 추가했다. 누르면 전자칠판에 띄우는 읽기 전용 전체 화면이 열린다(학급 방 자유 매칭은 제외).
    • 모집 중: 큰 참가 코드·QR·"현재 N명 참가"·참가자 이름(학생이 들어오면 실시간 갱신).
    • 진행 중: 토너먼트는 라운드별 대진표, 리그는 이번 라운드 경기와 순위표를 큰 글씨로 표시.
    • 종료 후: 시상대와 컨페티(한 번).
    • 조작 버튼 없음, 교사 화면에서만 열림(학생 화면에는 버튼 없음), 닫기는 우측 상단 버튼 또는 Esc.
  • 스플래시 화면 프롬프트 스킬: 전역 스킬 make-homescreen으로 Nano Banana용 스플래시 화면 이미지 프롬프트를 만들 수 있게 했다(앱 본체에는 아직 반영되지 않음).

v3 아키텍처 핵심 — "자릿수는 방(rooms)이 가진다"

  • 교사 설정은 sessions.digits(3 또는 4, DB 기본값 4)에 저장하고, 방이 만들어질 때 rooms.digits로 복사한다. submit_guess는 이미 잠근 방 행의 digits만 보고 형식 검사·중복 검사·승리 조건(strikes = digits)을 판정하므로, 진행 중인 방은 세션 설정이 바뀌어도 흔들리지 않고 방 코드/대회에서 자릿수가 일관된다.
  • generate_secret(p_digits int default 4)는 인자를 받고, judge_guess는 비밀번호 길이를 기준으로 판정해 함수 시그니처를 유지했다.
  • match_waiting_players와 tournament_create_match_room이 세션의 자릿수를 읽어 방 생성 시 전달하고, create_tournament는 p_digits를 받는다(기본값 4로 옛 호출도 동작).
  • 학급 방 설정 변경은 기존 규칙(컬럼 단위 GRANT + RLS: capacity = 0이면서 mode = 'free'인 세션만)을 그대로 따르므로 토너먼트/리그는 시작 후 자릿수를 바꿀 수 없다.
  • 클라이언트는 입력 칸(.guess-slot) 4개 고정 마크업을 없애고 renderGuessSlots(containerId, count)로 자릿수만큼 만든다. AI 후보 생성(generateAllCandidates)도 자릿수를 받아 재귀로 만든다(4자리 5,040개, 3자리 720개).

칠판용 보기 구조 — "새 데이터 없이 기존 대회 화면의 데이터를 다시 그린다"

  • 별도 조회나 DB 변경 없이, 교사 대회 화면이 이미 불러와 실시간 구독 중인 상태(tState: 대회·참가자·경기)를 전체 화면 오버레이(#t-board)로 다시 그린다. 상태가 바뀔 때마다 renderTournament()가 오버레이가 열려 있으면 renderBoardView()를 함께 호출한다.
  • 기존 렌더 함수(tBuildMatchRow, tRenderStandings, tRenderBracket, tBuildChampionLines)를 그대로 재사용하고 큰 글씨용 CSS(.t-board)만 추가했다. 시상대 그리기는 두 화면이 공유하도록 tFillPodium으로 분리했다.
  • 진행 중 경기의 추측 내용은 조회하지 않으므로 화면에 나올 수 없다. 참가 QR은 코드가 같으면 다시 그리지 않는다.
  • 대회 화면을 떠나거나(cleanupTournament) Esc·닫기 버튼을 누르면 닫힌다.

5. 개발 과정 (타임라인)

v2 이후 진행한 작업이다.

  1. 스플래시 화면 프롬프트 스킬 제작: 전역 스킬 make-homescreen을 만들었다. 처음엔 메뉴가 있는 홈 화면을 만들었지만, 사용자가 "첫 접속 시 보이는 스플래시 화면, 메뉴 없이 배경+제목만, 들어가기 버튼은 앱에서 구현"이라고 정정해 스킬을 수정했다.
  2. 3자리 모드 방식 논의(/plan): 사용자가 (1) 메인 화면 전역 드롭다운 vs (2) 기능별 선택 중 하나를 추천해 달라고 요청. 코드와 서버 함수를 조사해 "방 단위 설정"을 추천했다.
  3. 구현 계획서 작성: 위치별 하드코딩(클라이언트 16곳, 서버 3개 함수)과 서버 설계를 담은 .omc/plans/digits-mode-plan.md. 사용자가 기본값에 동의.
  4. 구현: DB 마이그레이션(digits_mode) → game.js 일반화 → 연습/방/학급 방 설정/대회 설정 UI → 배지 → README.
  5. 기본값 변경 요청: "세 곳 모두 기본 게임 모드를 3자리로". UI 기본 선택과 학급 방 생성(digits: 3)을 바꾸고, 친구 초대는 그대로 두었다.
  6. 전자칠판 화면 설명 요청: 보고서 v3의 "전자칠판용 교사 모니터" 아이디어가 구체적으로 무엇인지, 교사만 쓰게 할 수 있는지 사용자가 질문. 이미 있는 교사 조작 화면과 "보여주기 전용 큰 화면"을 구분해 설명했다.
  7. 칠판용 보기 구현: 사용자가 "학급 방(자유 매칭)은 제외하고 안내한 대로" 구현을 요청. HTML 오버레이 → CSS → renderBoardView → 교사 화면 버튼·Esc 연결 → 테스트 → 화면 캡처 → README 순서로 진행.

6. 주요 의사결정과 이유

  • 전역 모드 대신 방 단위 설정: 메인 화면은 학생도 쓰는 화면이라 학생이 바꿀 수 있고, 온라인 대전은 두 사람의 자릿수가 다르면 성립하지 않는다. 교사가 만든 방·대회는 교사 설정이 우선해야 하므로 전역 설정은 사실상 연습에만 의미가 있다. 반면 방/대회의 자릿수는 턴 시간·시도 횟수와 같은 성격의 설정이라 기존 설정 화면에 자연스럽게 들어간다.
  • 처음 제안 정정 — 랜덤 매칭 대기열 분리는 불필요: 처음에는 "매칭을 자릿수별 대기열로 분리"를 제안했으나, 코드를 조사해 보니 match_waiting_players는 한 학급 방(세션) 안에서만 짝을 짓는다. 자릿수를 세션에 저장하면 같은 방의 학생은 모두 같은 자릿수라 매칭 로직을 바꿀 필요가 없다.
  • 방에 자릿수를 복사: 세션 조인 없이 방 행(이미 잠금)만으로 판정하게 해 잠금·일관성 문제를 피했다.
  • 랭킹은 이번에 자릿수를 구분하지 않고 합산: 범위를 줄이기 위한 결정이며 후속 과제로 남겼다.
  • DB 컬럼 기본값은 4, 클라이언트가 3을 명시: 배포 직후 옛 JS 캐시가 방을 만들어도 옛 동작(4자리)과 호환된다. 친구 초대는 자릿수 UI가 없어 4자리를 유지했다.
  • 연습 모드 자릿수는 브라우저에만 저장(localStorage): 혼자 하는 설정이라 서버 저장이 필요 없고, 저장소를 못 쓰는 환경에서도 기본값으로 동작하도록 try/catch로 감쌌다.
  • 3자리일 때만 배지 표시: 4자리 화면의 변화를 최소화했다.
  • 칠판용 보기는 "보기 전용 + 교사 화면에서만 열림": 조작 기능은 이미 관리 토큰으로 교사만 쓸 수 있으므로 칠판 화면에는 조작 버튼을 아예 넣지 않았다. 대진표·순위는 학생에게 보여 주려는 정보라 "교사만 조회 가능"을 위한 별도 조회 토큰은 만들지 않고, 버튼이 교사 화면에만 있게 했다.
  • 별도 URL/창이 아니라 같은 화면 위에 덮는 오버레이: 새 조회 경로와 DB 변경 없이 기존 구독·데이터를 재사용한다. 교사가 한 기기에서 열어 전자칠판에 미러링하는 사용을 전제로 했다.
  • 진행 중 경기의 추측 내용과 시도 진행률은 표시하지 않음: 칠판을 보는 다른 학생이 힌트를 얻거나 상대 전략을 엿볼 수 없게 하고, 구현도 단순하게 유지했다.
  • 학급 방(자유 매칭)은 제외: 사용자 결정. 진행 중 경기 표시까지 다룰 때 위 정보 노출 문제가 더 커지기 때문이기도 하다.

7. 문제 해결 기록

  • 컬럼 단위 GRANT 문법 오류: grant select, insert, update on public.sessions (digits) to ...는 문법 오류였다. 올바른 형식은 grant select (digits), insert (digits), update (digits) on public.sessions to .... 마이그레이션은 한 트랜잭션이라 실패해도 일부만 적용되지 않았다.
  • isValidGuess 정규식 이스케이프: 자릿수를 정규식에 끼워 넣던 코드가 Python 문자열 처리 중 \d가 깨져 항상 실패했다. 테스트가 바로 잡아냈고, 정규식 대신 길이 검사 + 숫자만 검사 + 중복 검사로 단순하게 바꿨다.
  • 서버 형식 검사 위치: submit_guess의 형식 검사가 방을 잠그기 전에 있었는데, 자릿수를 방에서 읽어야 하므로 잠금 뒤로 옮겼다(예외 메시지는 유지).
  • 함수 오버로드 위험: generate_secret()과 create_tournament(...)는 인자를 추가하면 옛 함수가 남아 호출이 모호해질 수 있어 옛 함수를 drop한 뒤 다시 만들고 권한을 다시 부여했다(pg_proc로 오버로드가 하나뿐임을 확인).
  • 검증 도구 상실: 이전 세션의 jsdom 테스트 스크립트(37항목)가 임시 폴더에서 사라져 다시 돌릴 수 없었다. 새 테스트(21항목)를 다시 작성해 3자리 경로와 기본값을 확인했다.
  • 입력 칸 개수 고정 마크업: 슬롯이 HTML에 4개 고정이라 3칸으로 줄이려면 마크업을 비우고 JS로 렌더링하도록 바꿔야 했다.
  • 칠판용 보기 스타일 재사용: 대회 화면 스타일(t-*)이 .t-screen 안에서만 정의한 색상 변수에 의존해, 화면 밖 오버레이에서는 카드 배경이 비었다. 변수 정의와 [hidden] 규칙을 .t-screen, .t-board로 확장해 해결했다.
  • 큰 스크립트를 셸로 붙여 넣다 실패: 한 번에 여러 파일을 고치는 명령이 따옴표가 섞여 셸 파싱 오류로 아무것도 적용되지 않았다. 스크립트를 파일로 저장해 실행하는 방식으로 바꿨다(변경이 적용되지 않았음을 git status로 먼저 확인).

8. 보안/성능 고려사항

  • 서버 판정: 자릿수는 서버가 방 기준으로 검증한다. 3자리 방에 4자리 추측, 4자리 방에 3자리 추측, 3자리 방의 중복 숫자는 모두 예외로 거부된다(클라이언트가 조작되어도 우회 불가).
  • 권한: 새 컬럼 sessions.digits에만 컬럼 단위 SELECT/INSERT/UPDATE를 부여하고, rooms.digits는 SELECT만 부여했다(방 자릿수는 서버만 쓴다). 내부 함수의 EXECUTE 권한 규칙(v2)은 유지했다.
  • 설정 변경 범위: 학급 방의 digits 변경은 기존 정책(capacity = 0 and mode = 'free')으로만 허용된다. 다만 학급 방은 서버에서 교사와 학생을 구분하지 못하는 구조(로그인 없음)라, 방 코드를 아는 악의적 사용자가 API로 직접 자릿수를 바꾸는 것은 막지 못한다(턴 시간·시도 횟수도 동일한 기존 한계). 이미 열린 방은 rooms.digits가 고정이라 영향이 없다.
  • 칠판용 보기의 정보 노출: 화면에 나오는 데이터는 대회·참가자·경기 결과와 참가 코드뿐이다(모두 원래 학생이 조회 가능한 공개 데이터). 진행 중 경기의 추측 내용과 정답은 조회하지 않는다. 조작은 기존 관리 RPC(토큰 검증)만 가능하고 이 화면에는 조작 버튼이 없다. 닉네임은 textContent로 렌더링해 XSS를 막는다. 다만 "교사만 조회"를 서버에서 강제하지는 않는다(방 코드를 아는 사람은 원래도 대회 데이터를 조회할 수 있다).
  • 성능: AI 후보 생성이 재귀로 바뀌었지만 5,040개 수준이라 부담이 없다(3자리는 720개로 오히려 가볍다).
  • v2에서 이어진 보안 조치: 관리 토큰 인증, finish_room/forfeit_room 하드닝, 잠금 순서 통일, 참가 트리거.

9. 테스트 및 검증

  • DB 시뮬레이션(롤백 트랜잭션): 3자리 학급 방과 4자리 학급 방을 동시에 만들어 각각 방 digits, 비밀번호 길이, 잘못된 자릿수 추측 거부, 중복 숫자 거부, 정답 시 승리·방 종료를 확인. 3자리 토너먼트·리그(3명)에서 라운드 방이 모두 digits=3, 비밀번호 3자리임을 확인. 익명(anon) 권한으로 digits=3 세션 생성 확인.
  • 화면 시뮬레이션(jsdom, 21항목): 3자리 비밀번호 생성·판정·검증, AI 3자리 추측, 연습 3자리 슬롯/제출 조건/승리, 4자리 복귀, 방 슬롯·배지·제출 조건, digits 없는 옛 방의 4자리 호환, 토너먼트 p_digits 전달, 세 곳의 기본값 3자리.
  • 화면 캡처(Playwright + 임시 로컬 서버): 연습 설정 화면의 자릿수 토글, 3칸 입력 게임 화면(모바일 폭)을 확인.
  • 화면 시뮬레이션(jsdom) — 칠판용 보기 23항목: 교사 화면의 버튼 표시, 모집 중(코드·인원·참가자 칩·3자리 배지·QR 재렌더 방지·참가자 증가 반영), 토너먼트 진행 중(대진표 라운드 구역, 상태 문구, 조작 버튼 없음, 추측/정답 문구 없음), 리그(이번 라운드+순위표, 부전 +1점), 종료(시상대, 컨페티 한 번), 닫기·Esc·화면 이탈 시 닫힘, 학생 화면에서 버튼 숨김·열기 불가, 취소된 대회에서 버튼 숨김.
  • 화면 캡처(Playwright) — 칠판용 보기: 1600×900에서 진행 중 토너먼트(6명) 화면과 모집 중 리그(8명) 화면을 확인해 큰 글씨 배치와 QR 표시를 확인했다.
  • 미확인: 칠판용 보기를 실제 전자칠판/여러 기기에서 띄워 보지는 못했다(큰 화면 1600px 위주로만 확인). 큰 대회의 대진표가 한 화면에 다 들어오지 않을 수 있다. 옛 jsdom 회귀 테스트(37항목)는 재실행하지 못했다. 여러 실제 기기로 3자리 학급 방·토너먼트를 끝까지 진행하는 확인은 사용자 테스트에 의존한다. 데스크톱 폭에서 학급 방/대회 설정 화면의 자릿수 행 레이아웃도 별도 캡처는 하지 않았다.

11. 알려진 한계

  • 3자리와 4자리의 승패·랭킹이 합산된다(3자리 승리가 4자리 랭킹을 올릴 수 있음).
  • 친구 초대는 4자리 고정이다(자릿수 선택 UI 없음).
  • 학급 방은 교사/학생 구분이 없어, 방 코드를 아는 사용자가 API를 직접 호출하면 대기 중인 학급 방의 자릿수를 바꿀 수 있다(UI에는 노출되지 않음).
  • 3자리는 조합이 720개로 적어 시도 횟수 기본값(10회)에서는 쉬워질 수 있어, 교사가 시도 횟수로 조절해야 한다.
  • 교사가 브라우저 데이터를 지우면 대회 관리 토큰을 잃어 대회를 계속 관리할 수 없다.
  • 교사 브라우저를 새로고침하면 대시보드가 자동으로 열리지 않는다(허브의 "대회 화면으로 가기" 사용).
  • 토너먼트 연장전은 학생/교사 화면이 열려 있어야 자동 시작된다.
  • 접속을 끊은 상대 때문에 경기가 끝나려면 그 선수가 연속 3번 시간 초과해야 한다.
  • 로그인이 없어 같은 학생이 다른 기기로 접속하면 별도 사용자로 집계된다.
  • 칠판용 보기는 교사 화면에서만 열 수 있고 학급 방(자유 매칭)에는 없다. 큰 대회(16강 이상 등)의 대진표는 한 화면에 다 들어오지 않아 칠판 화면 안에서 스크롤해야 할 수 있다. 진행 중 경기의 시도 횟수 같은 진행률은 보여 주지 않는다.
  • 자동 UI 회귀 테스트가 저장소에 없다(테스트 스크립트는 작업 폴더 밖에만 존재하고, 이번에도 일부가 사라졌다).

12. 향후 개선 아이디어 / 업데이트 계획

다음에 하면 좋을 것

  • 랭킹·전적을 자릿수별로 분리(match_results.digits 추가 후 집계에 반영) — 난이도가 다른 승리가 섞이는 문제 해소
  • 화면 시뮬레이션/스크린샷 테스트를 저장소(tests/)에 포함해 회귀 테스트로 관리(이번에 도구가 사라진 문제를 예방)
  • 스플래시 화면(첫 접속 시 배경+제목+"들어가기" 버튼)을 앱에 구현하고 Nano Banana로 만든 이미지를 적용
  • 토너먼트 연장전/다음 라운드를 서버가 시간 기준으로 자동 시작(pg_cron)해 화면 의존 제거
  • 교사 대시보드 자동 복구 및 관리 토큰 백업/복구 수단

여유 있으면

  • 친구 초대에도 자릿수 선택 추가
  • 단계형 연습(3자리를 이기면 4자리 도전 제안)
  • 3자리 모드용 시도 횟수 기본값 제안(예: 7~8회)
  • 대회 결과를 이미지·인쇄용 화면으로 저장, 대회 전용 순위, 대회 이력 조회
  • 남은 화면(방 참가하기, 대기열, 경기 결과, 랭킹)도 같은 디자인 체계로 통일
  • 3·4위전, 스위스식 매칭, 자동 라운드 진행, 패자부활전

아이디어 수준

  • 칠판용 보기 확장: 학급 방(자유 매칭)용 화면(랭킹 상위 등), 별도 창/기기에서 여는 조회 링크, 큰 대회용 자동 스크롤·축소 보기, 경기별 진행률 표시(정보 노출에 주의)
  • 5자리 이상 확장 또는 교사가 정하는 숫자 범위(0~9 외)
  • 교사가 대회 옵션(연장전 횟수, 부전 승점 등)을 조정하는 고급 설정
  • 관전 모드
